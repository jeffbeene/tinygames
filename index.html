tinygames

An editor for JavaScript games small enough to fit entirely inside a QR code. No server, no database, no game IDs — the QR code is the game.

Everything you type is minified, compressed, and packed into the fragment of a /play/ link, which is what the code encodes. Scanning it decodes the game and runs it. Nothing is ever uploaded: the payload rides after the #, so it never reaches a server at all.

The largest QR symbol carries about 2.8 KB of compressed output — roughly 35–40 KB of readable JavaScript, which is a lot more game than it sounds. The bar under the code shows what you have spent, marked at the points where the symbol gets harder to scan. Big codes read fine off a monitor and badly off a print, so keep it in the green if you plan to put it on paper.

Runtimes

Both runtimes execute your game in an iframe sandboxed without allow-same-origin: it gets an opaque origin, cannot touch this page, and localStorage throws inside it. Code that arrives from a stranger’s QR code is untrusted by definition. Your choice is recorded in the payload, so a scanned game always boots the shell it was written against.

Canvas harness default
A full-bleed canvas, retina scaling, resize handling, an input map and the frame loop are already set up. They live on the play page rather than in the code, so they cost you no budget at all. Pick this for anything that draws.
Bare page
An empty document and nothing else — no canvas, no loop, no globals. The right choice when a game is DOM- or CSS-shaped. You write your own boilerplate, which costs 150–250 bytes of budget.

Canvas harness reference

Your code runs as a plain, non-strict script in the page’s global scope, which is why bare assignment (draw = () => {}) is how you hook into it.

Entry points

setup() Runs once, after the canvas has real dimensions.
draw() Runs every frame, in step with the display.
resized() Runs whenever the canvas changes size.

All three are optional, and all three are pinned against the minifier — no other top-level name you invent will survive the build under its own spelling. 

let x, y

setup = () => { x = W / 2; y = H / 2 }

draw = () => {
  clear('#0b0f16')
  x += (M.x - x) * 3 * dt
  y += (M.y - y) * 3 * dt
  c.fillStyle = '#7c9cff'
  c.beginPath()
  c.arc(x, y, 12 + sin(T * 6) * 3, 0, TAU)
  c.fill()
}

Canvas

c The 2D context, already scaled so you draw in CSS pixels and still get crisp edges on a retina screen.
W, H Canvas width and height, in CSS pixels.
clear(color) Fills the whole canvas with color, or erases it when you pass nothing.

Time

TSeconds since the game started.
dt Seconds since the previous frame, clamped to 0.1 so a backgrounded tab does not teleport everything on return. Multiply speeds by it.
FFrames drawn so far.

Input

K Keys currently held. Both spellings are populated, so K.ArrowLeft, K.a and K.Space all read true while down.
M Pointer, mouse and touch alike: M.x and M.y in canvas coordinates, M.down, plus M.px, M.py for where it was.

Presses are latched for one frame: a key or tap pressed and released between two frames is still visible to the next draw(), so fast taps are never silently dropped.

Sound and numbers

snd(freq, secs, type, gain) One short tone, enough for blips and thuds. Defaults are 440, 0.08, 'square' and 0.2; type takes any oscillator shape. Browsers only allow audio after a gesture, so sound starts once the player has touched something.
rnd(n) Random float from 0 up to n, which defaults to 1.
sin cos tan atan2 abs min max floor ceil round sqrt hypot pow sign random PI TAU Math without the prefix. Pure budget savings.

The one real gotcha

Read W and H inside setup(), never at the top level. Top-level code runs while the document is still parsing, before the canvas necessarily has a size. setup() is deliberately held back until the canvas has real dimensions, and resized() fires on every change after that. 

let cell
setup = () => { cell = W / 20 }   // correct
// let cell = W / 20              // wrong: W may still be 0
